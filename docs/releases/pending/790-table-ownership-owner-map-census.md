# fix(draft): the table-ownership contract names its real co-owners and an AST census enforces the map (#790)

## What changed
`DraftStore`'s module docstring claimed it "owns *all* Draft Room CRUD ... no other module writes these tables" — a sentence that was never true: 26 direct SQL write expressions against the six Draft Room tables live in three other production modules (8 in `api/routes/draft_room.py`, 7 in `services/draft_job_processor.py`, 11 in `services/draft_pipeline.py`). The docstring now declares the honest owner map, names a fourth writer that static analysis cannot see, and stops claiming exclusivity for stores that its declared co-owners duplicate. No runtime behavior changed: the production diff is the docstring only.

- **The docstring declares the map it actually has.** `DraftStore` is the default owner of `drafts`, `draft_jobs`, `draft_revisions`, `draft_events`, `draft_inputs`, `draft_findings`; it implements the atomic job claim, the status transition tables, revision-number allocation and audit-event recording, and the three co-owners are named with the tables/columns each one writes. The old paragraph claimed those four mechanisms "all live here" while the co-owner bullet eight lines below contradicted it — "implemented here" replaces "all live here", which describes what the module provides without claiming the co-owners do not also do it. The invariant "no caller may write an arbitrary status string" is now scoped to callers of the store, with the co-owners' mirrored prior-status allowlists stated explicitly instead of contradicting it.
- **A fourth writer is disclosed.** `services/job_lease.py` is a shared lease primitive parameterized on a table name, and the store constructs it with `table="draft_jobs"` for claims, heartbeats and reclaims. Because the table is a Python attribute rather than static SQL, no AST census can see it; the docstring says so rather than letting "three co-owners" read as exhaustive.
- **A new census test enforces the map in CI.** `backend/tests/draft_room/test_table_ownership_census.py` AST-parses `backend/app`, folds string expressions (implicit concatenation, f-strings, `+` chains, `.format()` templates) into static SQL, matches SQLite's write grammar — `INSERT [OR IGNORE|REPLACE|ABORT|FAIL|ROLLBACK] INTO`, `REPLACE INTO`, `UPDATE [OR ...]`, `DELETE FROM`, with the table in every static spelling SQLite itself writes (bare, quoted, backtick, bracketed, schema-qualified, comments allowed between verb and table) — and fails when a module outside the four-owner map writes these tables through static SQL. Docstrings and `#` comments are excluded by AST construction, so the `routes/vaults.py` comment a line-regex census miscounts is invisible by design.

## Behaviour change worth knowing
None at runtime. The changed surface is developer-facing documentation plus a new CI guard: adding a new module that writes a Draft Room table through static SQL now fails the census until the write is routed through `DraftStore` or the module is added to the declared owner map with a matching docstring entry.

Two guard properties are now pinned rather than assumed. `DraftStore` is described as the default owner, so its own write surface has a floor (40 sites, 48 today) — without it the store could be gutted of every six-table write and the census would stay green. And the census fails closed on unreadable files: a module that cannot be decoded or parsed names itself and reds the build, including UTF-8-BOM files, which CPython imports happily and which a strict `utf-8` read would misreport as a syntax error.

## Migration
No schema or settings change. No restart required.

## Caveats
- The census sees writes whose verb and table are static SQL text. A write assembled with a dynamic table (`f"UPDATE {table} ..."`, `.format(table=...)`) is invisible to static analysis — neither caught nor false-positived — and `job_lease.py` is a live instance of that boundary (disclosed in the docstring above). Prose inside a string literal can also match (`'delete from drafts: ...'` in a log message would fail the build). All of these named boundaries, plus SQL comments inside string literals, attribute-style docstrings, module-name indirection, cross-module SQL constants and symlinked directories under the scan root, are tracked in #926; the status-transition discipline that #790's constraints assign to the census but the census does not perform is tracked in #927.
- Two documentation surfaces carrying the same doc-vs-code drift are filed as #920 rather than smuggled into this PR (both doc-only, outside this issue's Files-expected-to-change): `specs/draft-room/SPEC.md` 4.1's `draft_store.py` row ("All SQLite CRUD, ...") and `draft_job_processor.py`'s module docstring, whose claim-mediation sentence is accurate for claims specifically but reads as full store mediation. SPEC section 10.3's copy of the status-transition invariant was added to #920's scope from the PR #921 review round.
