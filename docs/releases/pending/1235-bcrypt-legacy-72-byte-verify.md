# Legacy bcrypt logins for passwords over 72 bytes (#1235)

Issue: #1235 (follow-up from the dependency review of PR #1227; the failure is
already on master and is not caused by the passlib 1.9.5 bump).

## What changed

`verify_password` in `backend/app/services/auth_service.py` keeps passlib as
the first verifier. Its direct-`bcrypt` fallback now:

- runs only for bcrypt-format hashes (`$2a$`, `$2b$`, `$2y$`); any other hash
  that passlib could not verify fails closed with `False`, as before;
- passes the first 72 bytes of the UTF-8 encoded password to
  `bcrypt.checkpw`, which is exactly the secret bcrypt 4.x hashed when the
  legacy hash was stored. The cut is by bytes, so it can split a multibyte
  character, as bcrypt 4.x did.

argon2id verification is unchanged and never truncated.

## Why

bcrypt 5.0.0 (pinned in both lockfiles) raises `ValueError` for secrets longer
than 72 bytes, where bcrypt 4.x silently used the first 72. passlib 1.9.5 hands
the full secret to the bcrypt package, and its `truncate_error` option is a
hash-time policy only (it is already `False` by default and does not change
what is passed to the backend on verify; verified by probe). So users whose
legacy bcrypt hash came from a password over 72 bytes got a 401 on every
login. The password policy allows 128 characters, and non-ASCII passwords pass
72 bytes at 18 to 37 characters (four- to two-byte characters).

## Security notes

- A password that matches the original only in its first 72 bytes verifies
  against such a legacy hash. This is a property of the stored bcrypt hash
  (bcrypt 4.x never hashed the rest) and was already true before bcrypt 5.
- On the first successful login the existing rehash-on-login replaces the
  legacy hash with argon2id over the full submitted password, after which
  every byte counts.
- Wrong passwords, malformed bcrypt hashes and unknown hash formats still
  return `False`.

## Migration steps

None.

- `backend/tests/test_1235_legacy_bcrypt_long_password_login.py` drives
